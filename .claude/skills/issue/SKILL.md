# /issue コマンド

機能の説明を受け取り、要件解析→分割計画→ユーザー承認→親Issue+sub-issue作成を行います。

## 入力

- `$ARGUMENTS`: 実装したい機能の概要（自然言語）

## 手順

### 1. 要件解析

`$ARGUMENTS` から以下を抽出する:

- 機能スコープ（何を実現するか）
- 技術要件（使用するライブラリ、API設計、データ構造など）
- CLAUDE.md の既存アーキテクチャとの整合性

現在のコードベースを Glob / Grep / Read で確認し、既存の構造を把握する。

### 2. レイヤー分割に基づく分割計画の策定

以下の **4層モデル** の順序で sub-issue に分割する:

| 順序 | レイヤー | 内容 | レビュー観点 |
|------|---------|------|-------------|
| 1 | エンドポイント & DTO | API の入出力定義。実処理はモックで返す | バリデーションルール、レスポンス型は適切か？ |
| 2 | インフラ層 | Repository 実装（DB操作） | クエリは効率的か？型変換は正しいか？ |
| 3 | アプリケーション層 | ユースケース実装。モックを Repository に置き換え | ビジネスロジックの実装方法は妥当か？ |
| 4 | テスト | インテグレーションテスト（必要な場合のみ） | テストケースは十分か？ |

#### 分割の原則

- **API契約を先に決める**: PR1 でエンドポイントとDTO（バリデーション・レスポンス型）を定義し、モックレスポンスを返す。これにより設計レビューが最初に完了し、後続PRでの方針転換にも対応できる
- **レイヤーごとに切る**: 各PRのレビュー観点が自然に1つに絞られる
- **1PR あたり 40〜60行目安**: レビュアーが5〜10分で読み切れるサイズ
- **3〜5個の sub-issue に収める**: 多すぎるとレビュアー負担が逆に増加する
- **テストPRは独立**: ロジック変更とテストが混在しないようにする（テストが少量の場合はアプリケーション層PRに含めてもよい）

### 3. 分割計画をユーザーに提示

以下の形式で計画を提示し、**ユーザーの承認を得る**:

```
## 分割計画

親Issue: {機能名}（全体計画）

| # | sub-issue | 概要 | レビュー観点 | PR目安 |
|---|----------|------|-------------|--------|
| 1 | エンドポイント & DTO | {スコープ} | {何をレビューすべきか} | 〜XX行 |
| 2 | インフラ層 | {スコープ} | {何をレビューすべきか} | 〜XX行 |
| 3 | アプリケーション層 | {スコープ} | {何をレビューすべきか} | 〜XX行 |
| 4 | テスト（必要な場合） | {スコープ} | {何をレビューすべきか} | 〜XX行 |

この計画で Issue を作成してよろしいですか？
```

**ユーザーの承認を得てから次のステップに進むこと。**

### 4. 親Issue の作成

```bash
gh issue create \
  --repo inoue2302/ai-pr-split-demo \
  --title "{機能名}" \
  --body "{全体計画の本文}" \
  --label "planning"
```

親Issue の本文には以下を含める:

```markdown
## 概要
{機能の説明}

## 技術スタック
{使用する技術・ライブラリ}

## 分割方針
4層モデル（エンドポイント&DTO → インフラ層 → アプリケーション層 → テスト）でレイヤーごとにPRを分割。
PR1でAPI契約をモック実装で定義し、後続PRで実装を段階的に置き換える。

## sub-issues
- [ ] [1/N] {sub-issue 1 タイトル}
- [ ] [2/N] {sub-issue 2 タイトル}
- ...
```

### 5. sub-issue の作成

各 sub-issue を依存順に作成する:

```bash
gh issue create \
  --repo inoue2302/ai-pr-split-demo \
  --title "[1/N] {sub-issue タイトル}" \
  --body "{sub-issue 本文}"
```

各 sub-issue の本文には以下を含める:

```markdown
## 概要
このsub-issueの実装スコープ

## 親Issue
#{親Issue番号} {親Issueタイトル}

## 依存関係
- 前提: なし（1番目） / #{前のsub-issue番号} の完了後に着手（2番目以降）

## レイヤー
{エンドポイント&DTO / インフラ層 / アプリケーション層 / テスト}

## 実装スコープ
- [ ] 具体的なタスク1
- [ ] 具体的なタスク2

## レビュー観点
- このPRでレビュアーが確認すべきポイント

## 受け入れ基準
- 条件1
- 条件2

## PR目安
〜XX行
```

### 6. sub-issue の紐付け

GitHub sub-issues 機能で親Issue に紐付ける。
まず `gh issue edit --add-sub-issue` を試行し、フラグが存在しない場合は親Issue本文内の sub-issues リストにリンクを追記する形で代替する。

```bash
# gh CLI が --add-sub-issue をサポートしている場合
gh issue edit {親Issue番号} --repo inoue2302/ai-pr-split-demo --add-sub-issue {sub-issue番号}

# サポートしていない場合は親Issue本文に sub-issue リンクを含めているため紐付けは省略可
```

紐付けが失敗した場合は警告としてユーザーに通知し、処理は継続する。

### 7. 結果サマリーの表示

```
## Issue 作成完了

親Issue: #{番号} {タイトル}

| # | sub-issue | 番号 | レイヤー | 依存 |
|---|----------|------|---------|------|
| 1 | {タイトル} | #{番号} | エンドポイント&DTO | なし |
| 2 | {タイトル} | #{番号} | インフラ層 | #{前の番号} |
| 3 | {タイトル} | #{番号} | アプリケーション層 | #{前の番号} |
| ... | ... | ... | ... | ... |

次のステップ: `/implement {親Issue番号}` で実装を開始できます。
```

## 注意事項

- 分割計画は必ずユーザーの承認を得てから Issue を作成する
- sub-issue の依存関係（実装順序）を明確にする
- 各 sub-issue の実装スコープは具体的かつ過不足なく記載する
- PR1 はモック実装で API 契約を定義し、設計の柔軟性を確保する
- テストが少量の場合は独立したsub-issueにせず、アプリケーション層に含めてもよい
- 日本語で Issue を作成する
